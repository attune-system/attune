File management architecture

Durable bytes leave the pod.

PostgreSQL decides which bytes matter. Object storage keeps those bytes. Pods hold disposable caches and bounded staging files, so no Attune workload needs a shared ReadWriteMany volume.

one release-wide storage mode S3, GCS, or filesystem BlobStore exact object versions API-mediated worker access

The governing split

Metadata controls. Objects persist. Pods rebuild.

The design removes shared mutable directories. Each storage system has one job, and no service infers durable state by listing a bucket or inspecting another pod's filesystem.

01

PostgreSQL is authoritative

It owns active pack pointers, release pins, executable snapshots, artifact lifecycle state, log sequence numbers, checksums, object keys, provider versions, and retention state.

02

Object storage owns immutable bytes

BlobStore writes each pack archive, artifact body, and log segment once. Reads request the recorded provider version and verify size and SHA-256.

Runtime flows

Four paths replace three shared directories

Every path publishes immutable data before PostgreSQL makes it visible. Local atomic rename protects caches. Database transactions protect durable state.

Pack releases

  1. The API validates a staged pack and builds a deterministic archive.
  2. It writes packs/blobs/sha256/<digest>.tar.gz with create-only semantics.
  3. A transaction records the release, component projection, and active pointer.
  4. Executions and sensors retain the release ID, digest, and executable snapshot.
  5. Each consumer fetches the exact release through the API and extracts it into a temporary sibling.
  6. A ready marker and atomic rename publish the local digest-keyed cache.
<packs_base_dir>/.releases/sha256/<digest>/pack

Runtime environments

  1. The worker derives a cache key from the pack digest, dependencies, runtime, platform, and image format.
  2. It builds the environment in a temporary directory on the same local volume.
  3. It validates the configured interpreter and writes .attune-runtime-ready.
  4. An atomic rename publishes the cache. A concurrent winner is accepted only when its marker matches.
<runtime_envs_dir>/sha256/<cache-key>

Completed artifacts

pending→ ready→ deleting
  1. The API reserves an object key and a pending version.
  2. The producer writes a regular file in its pod-local staging directory.
  3. The API transport uploads the file to API-local staging, then requests completion.
  4. The API publishes the immutable object and verifies its size and SHA-256.
  5. PostgreSQL marks the version ready. Only then can normal readers see the body.
  6. Retention moves the row to deleting before the supervisor deletes the recorded object version.

Execution, sensor, and workflow logs

  1. SegmentedLogWriter buffers up to a byte or time limit.
  2. The producer sends sequence n through an authenticated API route.
  3. The API publishes one immutable object, then locks and advances the stream row.
  4. An identical retry succeeds. Different bytes or a skipped sequence return a conflict.
  5. Sealing flushes the tail and marks the artifact ready.
  6. A reader concatenates exact-version segments in sequence order and verifies each digest.
logs/<stream-id>/segments/<sequence>

Failure behavior

The invariants that make retries safe

The architecture assumes pods can die between any two operations. Each publication path either remains invisible or converges to the same result when retried.

CREATE ONLY

Objects do not overwrite

A conflicting write succeeds only when the existing size and digest match.

EXACT VERSION

Reads stay pinned

S3 version IDs, GCS generations, or supported ETags accompany every durable read.

VERIFY BYTES

Metadata is checked

Pack archives, artifacts, and log segments validate size and SHA-256.

PUBLISH LAST

Partial data stays hidden

Ready rows and cache markers appear only after byte verification succeeds.

DELETE TWICE

Cleanup survives retries

PostgreSQL records deleting before the supervisor removes an exact object version.

RECONCILE

Lost messages do not own state

Sensor replicas return to PostgreSQL desired state even when a lifecycle prompt disappears.

Expected log loss is bounded, not zero. A pod can lose bytes held in the current in-memory segment before its byte or time threshold triggers a flush. Committed segments remain durable and ordered.

Credential boundary

  • The API writes and reads pack, artifact, and log objects.
  • The supervisor performs HEAD checks and exact-version deletion.
  • Workers, sensors, and the executor authenticate to the API.
  • The chart creates Kubernetes service accounts, not buckets, keys, or cloud IAM bindings.

Current implementation

Implemented safeguards and remaining limits

Issues #40 through #50 closed the defects found during the initial Kubernetes proof. The code now enforces these safeguards.

  • Explicit API pack and artifact transports fail startup when URL or token configuration is incomplete. They never fall back to pod-local volume storage.
  • Pack, artifact, log, and migration object I/O streams with bounded memory. Range requests reach the storage provider.
  • Startup checks stable provider-version support, including enabled S3 bucket versioning and GCS generations.
  • Zero-byte artifacts become ready immutable objects. Cleanup targets the recorded object version and cannot delete a replacement.
  • Pack activation publishes the API-local projection only after its database transaction commits.
  • Supervisor retention preserves active and pinned releases. A safety-windowed metadata ledger collects unreferenced object versions without bucket listing.
  • Execution, sensor, and workflow logs enforce configured byte and time limits, persist their effective limits and failures, and expose the bounded in-memory loss window without an unused log volume.
  • Optional runtime persistence gives each worker or sensor pod its own RWO claim. emptyDir remains the default.

What the disruption soak proves

A disruption cycle deletes one disposable application pod, waits for Kubernetes to replace it, runs fresh work, and checks durable state before moving to the next service. The cycle covers the API, action worker, sensor worker, executor, and supervisor. PostgreSQL, RabbitMQ, and object storage remain available; this is a pod-recovery test, not a database or regional-outage test.

  • Executions and sensors continue using their pinned pack release without mixing cached files from another release.
  • Completed artifact bytes and digests survive replacement, and exact-version cleanup never removes a newer object.
  • Log segments remain readable, ordered, contiguous, and within the documented uncommitted-loss bound.
  • Interrupted uploads converge through retry or supervisor cleanup instead of accumulating indefinitely.
  • Local pack and runtime caches rebuild from immutable object storage without an RWX filesystem.

The 24-hour duration repeats those checks across many token refresh, retention, reconciliation, retry, and cache-churn cycles. Its purpose is to catch gradual memory or metadata growth and low-frequency races that a five-cycle smoke test cannot expose.

Two limits remain. The latest local proof passed 14 disruption cycles over 360 seconds and replaced every targeted application pod at least twice, but issue #39 still requires a 24-hour soak. The regenerated attune-0.7.0.tgz and index.yaml are working-tree artifacts in attune-charts; no published package release contains this implementation yet.
