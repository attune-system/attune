# Minimal delegation and local process isolation remediation

**Status:** Revised proposal; no runtime changes or security closure established.

**Decision:** Three separately reviewable deliverables: verify and enforce admitted delegation; restore operational pack-managed queues with authorized business-owned configuration; and finish the existing local Linux sandbox around pack-controlled processes. Keep the existing worker and sensor managers. Kubernetes/Compose continue to run persistent services; actions require no new Pod, container, remote launcher or scheduler.

## 1. Scope and finding mapping

The supplied Mantis verification report (`e6bb5280-fa1f-4332-860d-1cb9f7da9d61-summary-report.md`, review `app-3d296835f0744e428972222611867839`, tested commit `0c75567feed1a25a88aaf82fc38a6942f3e1b0ff`) reports **VF-1/VF-2: cross-pack escalation through `standard` delegation**. It is not the source report for **s-2/s-23: process inspection/interference**, which the previous version of this plan addressed. Keep their evidence and closure separate.

- **VF-1:** the report alleges unauthorized target pack/action Key, cache and artifact access through direct and child execution. Distinguish admitted action/workflow capabilities from unauthorized authority expansion before selecting a fix; a process sandbox cannot fix an API authorization bypass.
- **VF-2:** queue and rule producer paths may bypass that ceiling. Enforce the same target checks at configuration and durable acceptance boundaries, including resolved defaults.
- **s-2/s-23:** pack processes may inspect siblings or manager files, signal other workloads, or modify shared runtimes. Finish local process/filesystem isolation, including setup and verification. Recover the original reports before claiming complete closure; their full text is not supplied here.

This plan belongs to this thread's worktree. Its baseline has the existing local `workload_sandbox` wrapper, not `crates/workload-backend` or `NativeEffectsRequired`. The abandoned adapter attempt is background only: do not import it or add its removal tasks to this implementation.

## 2. Delegation and composition: authorization fixes plus queue restoration

### Preserve intentional workflow, action and sensor capabilities

**Confirmed product requirement:** workflows may invoke reusable actions from any provider/integration pack and grant those invocations access to credentials owned by the containing workflow/pack. Provider packs supply integration functionality; credential ownership belongs to the consuming business/workflow context and need not belong to the provider pack. This applies uniformly to Salesforce, ServiceNow, Slack and other API providers, without provider-specific authorization exceptions. For example, `business.sync_accounts` may call `salesforce.query` with authorized access to the business pack's Salesforce credentials. The connector does not need to own those credentials. This access must work through both authorized secret input materialization and scoped runtime Key API access, where selected; receiving a secret parameter does not by itself grant API permissions.

The current [delegation contract](../permissions/delegation-and-secret-disclosure.md#reserved-standard-invocation-authority) already gives a workflow child its own action/pack scope plus its immediate containing workflow action/pack under selected `standard` access. It also treats `standard` as an invocation capability: a caller may invoke an authorized trusted action without personally holding all of its Key grants. Preserve these semantics. **Withdraw the earlier proposal to require every invoker to possess every target `standard` grant or require all cross-pack workflow children to fit solely within the parent's pack selectors.** Either restriction would reject intentional capability-bearing invocations.

The security boundary is the authorized, immutable executable/workflow and its admitted permissions, together with the active execution/producer fences. A workflow author may grant a child the workflow's admitted capabilities for that invocation. An arbitrary caller cannot manufacture workflow lineage, obtain the human owner's unselected authority, or turn the child's temporary workflow access into an unrelated durable grant. Authoring/publication and explicit additional permission admission remain trust boundaries; adding an action to a workflow is a decision to trust that action with the credentials supplied to it.

Keep immediate containing-workflow scope rather than automatically unioning every ancestor, sibling or unrelated pack. Additional permissions use existing selected named refs/recorded admissions and their containment checks; no new grant format, compatibility layer or permission service. Direct invocation of a provider action outside the business workflow gains no business-pack scope from its action name or provider identity alone.

### Business rules configuring provider sensors

**Confirmed product requirement:** business-process packs may configure reusable sensors from any provider pack through rules, supplying credentials owned by the business pack. Provider implementation ownership and credential ownership are independent for sensors as well as actions. An authorized business rule may, for example, configure a ServiceNow or Slack sensor with its business-owned connection credentials; relocating those Keys into the provider pack must not be required.

Preserve server-rendered rule/sensor settings and their captured input authority. Resolve only authorized referenced secrets, retain exact rule/configuration and Key origins, and bind delivery to the admitted sensor generation and current configuration delivery. Reuse the existing sensor schema, rule-delivery and origin repositories. This is authorized configuration delivery, not implicit permission for the sensor token to enumerate or decrypt every Key belonging to the configuring business pack. Additional runtime API access, where needed, must use explicitly admitted sensor-purpose grants; do not copy workflow `standard` scope rules into sensor credentials.

One provider sensor process can serve multiple business rules. Keep settings associated with their actual rule and source pack rather than overwriting a global provider credential or merging participating packs' authority. Code receiving several authorized configurations is trusted with those delivered values; this plan does not claim that a single shared sensor process isolates those values from its own code. Preserve that delivery model without adding a process/Pod per rule. An unrelated rule, API caller or sensor generation must not gain another rule's protected configuration merely by sharing a provider or trigger. Configuration updates, refresh, restart and revocation must retain the existing admission, provenance and disclosure fences.

### Business queues configuring provider actions

**Confirmed product requirement:** a queue managed by a business pack accepts schema-validated structured records and dispatches executions whose action may belong to any reusable provider pack. The queue's admitted configuration may supply credentials and other secrets owned by the queue-managing business pack. Provider actions must not be required to own those credentials or receive them in every submitted queue record. This is the same composition model as workflow-to-action and rule-to-sensor configuration.

Keep record validation/mapping, trusted queue configuration and execution API permissions distinct. Resolve authorized secret references from the queue's admitted configuration alongside the record-derived parameters into the flat execution parameter map, preserving secret stdin delivery and recorded origins. The record submitter must have enqueue authority but need not personally obtain plaintext business credentials when an admitted managed queue is authorized to supply them. Untrusted record fields cannot replace protected configuration, select arbitrary Key refs, widen API grants or change the admitted target. Any intentionally dynamic selectors must be bounded by the existing schema, mapping and admission policy.

### Queue baseline and required restoration

**Current limitation:** pack-defined queues (`is_adhoc = false`) cannot accept new items: `crates/api/src/routes/work_queues.rs` explicitly returns `NotImplemented` for recorded queue sponsorship. Repository admission in `execution_runtime_admission.rs` and dispatch in `queue_dispatcher.rs` also require default-disabled `RecordedConsumerReadiness`. This is a code gate, not the ordinary queue enabled/paused setting or a deployment configuration switch. API/UI-created ad hoc queues retain a delegated path, including schema validation and batching, but that path has not been verified end to end for this revision and does not establish managed business-pack credential authority.

**Working managed queues are a required deliverable, not indefinite deferred scope.** Track their restoration separately from narrow delegation corrections and sandbox integration. Reuse existing recorded-authority machinery, but do not delete the gate, hardcode readiness flags, or substitute older broad credentials to make enqueue succeed. Complete coordinated admission, API consumers, artifact disclosure, runtime-read provenance, notifier delivery, worker completion, native executor consumers and candidate-isolation readiness, as applicable to the existing readiness contract. An unavailable required consumer must still reject the operation before accepted work or secret delivery. Follow the existing [authority cutover](../deployment/postgresql-only.md#execution-authority-cutover); do not reset the database or downgrade retained recorded work to delegation.

### Queue configuration admission contract

Existing machinery is a starting point, not proof that queue-owned secret delivery works. `ExecutionAdmissionRepository::admit_queue_item` in `execution_runtime_admission.rs` binds `InvocationBinding::Queue` through `RuntimeTarget::Component(Queue, id)` and persists `work_queue_item_runtime_admission` with policy revision, selected authority and digest. However, the currently gated route captures/copies **contributor** authority through `RecordedInputAuthorityRepository`; dispatch resolves configuration and Keys against those contributors. That does not supply the business queue's independently admitted configuration authority.

Before implementation, map the existing runtime policy revision, queue target/configuration bindings and purpose-qualified input receipts to the following required proof. If they do not retain a necessary field or capability, extend the owning canonical v1 record and repository narrowly; identify any schema change and SQLx preparation explicitly. Do not claim an existing queue input-admission proof until that mapping is demonstrated.

- Authorized deployment/configuration admission binds the actual managing queue/pack, immutable configuration and mapping revision/digest, allowed secret selectors and captured input grants, pinned target executable/schema, and selected runtime API permissions. Enqueue atomically retains the corresponding binding for each accepted item; dispatch validates it and its liveness before effects.
- Queue-supplied configuration secrets resolve using that admitted configuration capability. Contributor-controlled secret references and record data retain their separate contributor authorization and provenance. Never union the two into ambient grants or require enqueue-only users to hold plaintext rights to the queue's fixed admitted credentials. Sharing a batch must not let one contributor authorize another's arbitrary selector.
- Accepted items retain their configuration/authority binding through batching, retries and redelivery. Later configuration edits cannot silently reinterpret them; preserve existing drain/re-admission restrictions. Payload edits/upserts validate the new contributor-controlled values and selectors without borrowing an earlier contributor's authority or replacing protected configuration. Revocation between acceptance and dispatch prevents new protected effects according to the existing admission contract.

For ad hoc queues retain attributed requester checks; merely associating one with a business pack does not establish managed authority. Never transfer ambient manager or installer permissions into executions. Where a dispatched action needs runtime Key API access rather than supplied secret parameters, select explicit admitted grants scoped to the necessary business-pack resources; queue association alone does not expand `standard` scope. Implement through existing repositories with no new controller, grant service or per-record infrastructure.

### Minimal implementation

1. Reproduce VF-1/VF-2 on the implementation revision and classify each result against the intended capability contract. Merely invoking an authorized action that uses its own Keys, or a legitimate child using its containing workflow's Keys, is not by itself unauthorized escalation. Record any mismatch between the report's assumptions and this product policy; do not impose its proposed blanket restriction as the fix.
2. Reuse canonical repository standard-scope expansion and existing claim validation. Resolve the actual execution action, immediate containing workflow, persisted task/parent relationship, selected refs and active attempt from retained state. Deny forged lineage, expanded signed selectors, missing source context and unrelated pack access before secret delivery. Signed scope arrays alone are not authority. Preserve child target Execute checks and the admitted workflow target checks; neither a caller-supplied parent ID nor the `standard` string proves an authorized task edge.
3. For permissions explicitly delegated from the parent, validate containment against its admitted selected authority, without borrowing the owner's wider IAM grants. Keep the child's authorized own/containing-workflow `standard` capability distinct from that comparison. Verify `DelegatedExecutionRepository::select`, `validate_child`, direct admission, retries, workflow/callback producers and their credential consumers enforce the same distinction. Fix concrete omissions in existing helpers and transactions; do not add a second authority store.
4. Check queue/rule create, target/permission updates, enqueue, `accept_queue_item` and deferred acceptance/dispatch against the producer's actual authorization and retained sponsorship. A queue item or rule is not a workflow child merely because an execution submitted it; never import that execution's workflow scope without an existing explicit admission. Resolve defaults and actual pinned targets. Preserve the existing Access-only rule-creation restriction and durable queue sponsorship/revocation contracts. Avoid an unconditional live-parent requirement after valid durable acceptance.
5. Verify rule-to-sensor configuration admission, initial stdin delivery, configuration refresh and generation restart preserve authorized cross-pack secret inputs. Reuse `sensor_schema` and `sensor_rule_origin` checks to bind each delivery to the exact rule, source pack, sensor and generation; fix concrete gaps without introducing another authorization store. Do not substitute the provider pack's ownership or ambient manager authority for the configuration's admitted input grants.
6. Deliver queue restoration as its own change: establish the configuration-admission proof above, implement configuration/contributor authority separation, complete coordinated recorded consumers, and replace the unconditional enqueue rejection only when the supported path passes admission-through-completion tests. Preserve rejection for missing prerequisites. Cover both managed and existing ad hoc queues; no functionality claim based solely on repository fixtures or a successful enqueue response.
7. Verify protected output/artifact channels retain recorded Key origins and enforce disclosure checks. Keep public output classification controlled by the admitted `out_schema`/channel policy. The workflow may intentionally expose an approved nonsecret result derived from a credential; do not introduce whole-execution taint based on input secrets or API access.

The report proposes broader origin propagation. Fix concrete omissions for protected channels, but do not claim that metadata prevents arbitrary network exfiltration once authorized code receives plaintext. A requirement that every secret-derived public value become private conflicts with the existing schema-driven output contract and requires a separate decision. Cross-pack action/sensor reuse through workflows, rules and queues, with authorized secret delivery, remains supported during remediation.

### Acceptance

Use API/repository tests with owned dummy Keys and business, generic provider and unrelated pack fixtures. Exercise more than one provider pack to establish that authorization is independent of the provider identity; no live external API or provider credentials are needed. Required positive cases:

- An authorized business workflow calls actions from different provider packs using `standard`; each child can access its own and the immediate containing business workflow's action/pack Keys through the scoped API. Provider packs need not own the business credentials.
- Authorized secret parameters reach the connector through stdin with provenance preserved. Empty API permissions still omit the token; passing a credential does not implicitly enable Key reads.
- Business-pack rules configure sensors from different provider packs with authorized business-owned credentials. Cover initial launch, dynamic delivery/refresh and restart, including two business packs configuring the same provider sensor with different credentials and retained per-rule origins. Secret configuration delivery alone grants no broader sensor Key API scope.
- Business-managed queues turn schema-valid records into provider-action executions with business-owned credentials supplied by admitted queue configuration. Cover two enqueue-only users in one batch, distinct business queues sharing one provider action, retries and redelivery. Test configuration changes after acceptance, payload edits/upserts and revocation between acceptance and dispatch. Verify exact secret origins, accepted configuration bindings and explicitly selected API grants.
- Explicitly admitted additional parent grants, supported workflow retries and separately admitted managed execution keep working. A caller invoking a trusted action need not personally possess all its internal Key grants.

Required negative cases: the same connector invoked outside the workflow cannot read business Keys; forged task/parent relationships and expanded signed scope arrays fail; siblings, unrelated packs and unadmitted ancestor scopes remain inaccessible. Named-ref delegation cannot exceed admitted source authority. An execution cannot convert temporary containing-workflow scope into unrelated rule/queue authority. Include omitted/default refs, target-changing updates, source revocation and protected output/artifact disclosure. For sensors, reject unauthorized business-Key references, forged rule/source-pack bindings and stale-generation configuration reads; prevent unintended disclosure of another rule's settings through configuration APIs, events or logs under the existing schema/origin policy.

For queues, reject attempts to substitute protected credentials through record fields, inject unauthorized Key refs, change the target or widen permission selections. A queue in another business pack or an ad hoc pack association cannot borrow the admitted queue's authority. Ensure queue item views, acknowledgements and errors do not disclose configured credentials; apply existing protected-output and origin policies.

**Queue release gate:** run the real pack publication/admission → single and bulk enqueue → schema/mapping and credential resolution → dispatch → worker or native workflow execution → protected completion/acknowledgement → terminal item-state path on owned infrastructure. Assert credential provenance and lease fencing, replay-safe acknowledgements, bounded retries and honest failure states. Include API-created queue regression coverage and missing-consumer readiness rejection without committed acceptance. Enqueue-only and mixed-requester cases must actually execute with admitted queue credentials; declarations, mocked gates and skipped tests are not passing evidence.

Re-run the report's direct, child, queue and rule cases and check actual persisted outcomes and secret delivery, not only HTTP status. Record legitimate invocation behavior separately from exploitable bypasses. Fix and close only confirmed violations of the agreed contract; if a reproduction is intended behavior, document that disposition with the exact authorization and trust boundary rather than claiming the behavior was removed.

## 3. Process remediation: finish the shared local sandbox

### Keep the launch path local

Use `crates/common/src/workload_sandbox.rs` and `ChildProcessEnvironment`, with the existing worker/agent/sensor process, capture and completion code. Start with Bubblewrap, which already provides the namespace/mount mechanism. Attune supplies a fixed policy; Bubblewrap alone is not a security policy. See its [upstream security model](https://github.com/containers/bubblewrap#sandbox-security).

The steady-state path is **existing admission → local sandbox spawn → selected executable → existing capture/completion**. For ordinary actions, reuse preinstalled interpreters and already-supported cached runtime environments where their existing contract permits it. Those paths need no image transfer or new dependency setup for each invocation. Lifecycle recipes are a separate execution class: preserve fresh private nonreused generations, their stable physical paths, and preparation for each recipe invocation under the toolchain contract. Do not introduce lifecycle caching in this remediation. A sensor gets one sandbox per process generation, not one per emitted event.

### Deployment feasibility gate

Proceed with implementation against Bubblewrap on the working assumption that the target deployment can support it. Use the host fixture for development and validate the packaged worker on the intended GKE worker pool and supported Compose profile before rollout. The fixture must cover read-only execution, an owned writable preparation mount, and manager or launcher death with detached descendants. The restricted Kubernetes test denied nested user-namespace creation before reaching private procfs. Identify the denying policy and verify the full fixture in the supported profile.

Require non-root operation and dropped outer capabilities. The profile excludes privileged mode, host namespaces, control sockets, blanket unconfined policy and host `CAP_SYS_ADMIN`. Document any narrowly scoped operator profile prerequisite. Enable the isolation profile and claim candidate-isolation readiness only after the real deployment and candidate preparation paths pass. Injected agents must pass the same prerequisite checks. Kubernetes and Compose schedule persistent services, and each action starts a local child process.

### Shared boundary, including preparation

- **Processes:** private user, PID, mount, IPC and UTS namespaces, private procfs, dropped capabilities, no privilege escalation and no further namespace escape. Exclude manager namespace handles, inherited sockets and descriptors; expose only intended stdio and fixed launcher descriptors. Apply workload loader/interpreter variables after isolation, never to the outer launcher.
- **Files:** allowlist public OS/runtime inputs and only the selected pack/runtime. Mount published inputs read-only; give each invocation private scratch and owned outputs. Exclude manager configuration, homes, credentials, service-account tokens, custody spools and sibling directories. Validate aliases/links and ownership against mutation races. Never bind the full outer filesystem.
- **Environment/authority:** retain cleared environments and early parent dumpability protection. Preserve stdin JSON, nonsecret CLI exceptions, selected API permissions, secret origins and attempt fences. Setup/probes receive no final-action secrets or API token. Managers retain their existing DB/MQ/signing/encryption responsibilities behind the boundary.
- **Preparation:** run dependency hooks, runtime recipes, verification and candidate-test executables through the same wrapper in an owned unpublished writable stage. Stop all writers before validation/publication; invocation cannot modify the prepared inputs. Lifecycle generations remain private and nonreused; their preparation and invocation mounts preserve the same stable physical paths. Preserve runtime paths and supported script/link semantics under the existing [toolchain contract](../deployment/runtime-toolchains.md).
- **Networking/resources:** preserve required network access and existing limits. Audit reachable manager listeners for authentication. Shared networking does not block internal destinations or exfiltration; kernel exploits and comprehensive per-action availability/network isolation are outside this change. No new network controller, cgroup manager or configurable sandbox policy language.

Retain the sandbox's API artifact transport prerequisite initially. File producers upload through existing authenticated APIs; avoid adding a filesystem export helper or transfer container. Preserve encrypted log custody and finalization independently of process exit. Document the transport requirement when activating the deployment profile. With an empty permission selection, no execution token is issued: tokenless actions can produce captured structured/stdout results, but cannot upload file artifacts through this profile. A declared or attempted file-upload requirement must produce an actionable admission/authorization error; never silently grant `standard` or widen permissions. Test authorized uploads and tokenless denial. If retaining tokenless file-artifact export is a required existing contract, resolve it explicitly before activation; do not silently lose expected files or add a transfer service as a workaround.

### Supervision without a new lifecycle platform

Keep existing attempt/sensor-generation ownership, cancellation, timeout and capture. Tie a trusted launcher lifetime to the entire private PID namespace; on cancellation, timeout or manager death, terminate that namespace and await cleanup before publishing or deleting writable state. Detached descendants must not survive. The kernel kills namespace members when namespace init dies, but the actual Bubblewrap supervision chain still requires testing. See [Linux PID namespaces](https://man7.org/linux/man-pages/man7/pid_namespaces.7.html).

Prefer existing Bubblewrap supervision and local child handles. Add a small fixed local helper only if the feasibility test proves a required gate or cleanup guarantee is missing. No custom IPC protocol beyond the minimum fixed launch gate, no reattachment service and no new durable resource registry. Preserve existing input-once fences: attach capture before release, never retry ambiguous stdin delivery. After restart, report interrupted/uncertain work through existing recovery; do not reattach or relaunch by numeric PID. Retain uncertain staging rather than deleting it on an unverified PID/name match.

### Minimal code and deployment changes in this worktree

1. Harden the existing common sandbox wrapper and its descriptor/lifecycle handling once. Preserve admission, stdin delivery, capture, custody and completion in their current owners.
2. Route native/interpreted/command/inline actions, managed sensors, dependency/setup hooks, runtime verification and candidate tests through it. Inventory command sinks, including API-side pack handling; any reachable unsandboxed pack-code path remains denied in the isolation profile. Operator-owned fixed probes should not become another execution framework.
3. Package Bubblewrap and prerequisite checks in existing images/host installation. Validate Compose and the sibling Helm chart; update deployment docs and AGENTS.md with the implemented boundary. No Pod/container adapter, Runner package, provider RBAC or provider configuration removal is required in this tree. No database reset or migration rewrite is included.

### Acceptance and performance

Use owned processes and dummy secrets. Prove manager/sibling environment, memory, descriptors, signals and private files are inaccessible; published runtimes resist writes; setup hooks and sensors receive the same boundary. An intentionally exposed control must recover its dummy marker so host ptrace restrictions cannot produce a false pass. Exercise timeout, cancellation, detached children, manager crash/restart and capture failure; verify no surviving writers and honest uncertain/incomplete results. Missing sandbox prerequisites must reject startup/admission without executing pack code.

Retain functional tests for native CLI bindings, interpreted actions, secret stdin, scoped API use, authorized artifacts, tokenless file-upload rejection and log finalization. Add a lifecycle setup-to-invocation test covering generated absolute shebangs, supported links, writable preparation followed by read-only invocation at stable paths, nonreuse, and cleanup only after descendant termination. Confirm many actions run in the same persistent worker without action-driven Kubernetes/Docker API calls. Bare-host operation requires neither daemon.

Measure warm native `core.echo` and interpreted no-op dispatch-to-completion at serial and representative concurrent load, plus a separate lifecycle preparation/invocation case and one sensor startup. Report cached/preinstalled and nonreused lifecycle execution classes separately; do not claim savings by omitting required preparation. Record sandbox overhead, p50/p95/p99, throughput and peak resources separately from queue time. Compare equal behavior on the same host/revision; use the unsandboxed path only as a diagnostic baseline. Agree a measured latency/throughput budget before activation. Do not promise a speedup without results or build a benchmark platform for this change.
