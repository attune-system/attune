Rule-specific sensor placement

How rules, triggers, sensors, and sensor workers fit together today, and what Attune needs before a rule can choose where its sensor workload runs.

Status: proposal for review   |   Scope: sensor placement and ownership

Short answer

A rule cannot select a sensor worker today. A rule selects a trigger. The trigger may belong to a sensor, and the sensor's pack and sensor-level placement fields decide which sensor workers are eligible.

Sensor workers expose the same labels and taints used by action workers. They also use the same selector, toleration, and affinity types. The scheduling behavior is not the same. The executor selects one action worker, while every matching sensor worker may start its own copy of a sensor.

Rule-specific placement therefore needs more than new rule columns. Attune first needs a durable sensor workload assignment with exclusive ownership, health-aware selection, and failover.

The API should also reject a rule create, rule activation, or pack deployment when no sensor worker can currently run the requested trigger and effective placement. Pack deployment must preflight every contained rule and fail atomically if any managed-sensor rule cannot run. This admission check must use the same eligibility code as the sensor scheduler.

Current architecture

A rule references exactly one trigger through trigger_ref. The trigger may link to one managed sensor. The sensor process receives every active rule for its linked triggers through ATTUNE_SENSOR_TRIGGERS.

Current rule-to-process path

Placement applies to the pack and sensor. It does not apply to an individual rule.

Why rule fields are not enough

One sensor process currently handles many rules. A rule-level selector becomes ambiguous as soon as two rules require different locations.

The conflicting-rule case

A single process cannot truthfully satisfy both rule constraints.

The system also lacks exclusive ownership. If two workers satisfy the same rule selector, both can run the sensor. A preferred affinity score cannot fix that because the sensor services never compare candidates.

Two coherent design options

One process per sensor

Combine the pack, sensor, and every active rule's hard constraints. Select one worker that satisfies all constraints.

This is the smaller change, but conflicting rules make the whole sensor unschedulable. One new rule can disrupt existing rules.

Partitioned sensor workloads

Group rules by compatible effective placement. Assign each group to one worker and pass only those rules to its process.

This matches the requested behavior. Rules may use different workers without pretending that one process satisfies incompatible constraints.

Recommendation: model partitioned sensor workloads. Start with one workload per sensor if delivery needs a smaller first phase, but make assignment and process identity capable of supporting more than one workload.

API admission check

Rule creation and activation should pass through the API. Before the API creates any rule, including a disabled rule, it should prove that at least one current sensor worker can run the rule's trigger workload. Activation must repeat the check because worker availability may have changed since creation.

The API should also run the check when an enabled rule changes its trigger, sensor placement, or trigger parameters that affect runtime requirements.

Pack upload and registration are still API operations. Before changing pack state, the deployment path should preflight every contained rule through the same rule application service as direct rule creation. If any managed-sensor rule has no compatible worker, the API should reject the entire deployment. It must not install the pack partially.

Create or enable a rule, or deploy a pack

Admission gives the caller an immediate answer. Assignment still provides the durable runtime guarantee.

Eligibility criteria

A worker is compatible only when all of these checks pass:

  • The trigger belongs to an enabled managed sensor.
  • The worker has worker_role = sensor and active status.
  • The heartbeat is fresh and the worker is not cordoned.
  • The worker supports the sensor runtime and version constraint.
  • The worker satisfies the sensor-owning pack, sensor, and rule placement constraints.
  • The worker has capacity for the resulting sensor workload.

Failure contract

If no worker qualifies, the API should return 422 Unprocessable Entity. The response should contain stable reason codes and a redacted summary of why candidates failed.

{
  "error": "no_compatible_sensor_worker",
  "message": "No sensor worker can run this rule",
  "details": {
    "trigger_ref": "network.device_event",
    "sensor_ref": "network.device_sensor",
    "reasons": [
      "required_label_mismatch",
      "runtime_version_unavailable"
    ]
  }
}

For a pack deployment, the response should identify every rule that failed preflight so the author can fix the pack in one pass.

Rules whose triggers do not use managed sensors do not need a sensor worker. If such a rule requests sensor placement, validation should reject the rule as invalid rather than report worker incompatibility.

Admission is not reservation A worker can fail between the compatibility check and assignment. Use one shared eligibility implementation, then recheck inside the assignment transaction for an enabled rule. If assignment cannot complete, fail the API request rather than committing an enabled but unscheduled rule. A disabled rule passes the availability check but does not acquire an assignment.

Recommended architecture

The target design separates desired work from a running process. A scheduler builds sensor workloads from active rules, selects one eligible worker for each workload, and records a leased assignment. A sensor worker starts only workloads assigned to it.

Target control and runtime paths

Solid green arrows are assignment flow. Dashed arrows are lifecycle and heartbeat signals.

Scheduling and lifecycle flow

  1. The scheduler loads each enabled sensor, its owning pack, and the enabled rules for its triggers.
  2. It calculates effective placement for each rule from the pack, sensor, and rule constraints.
  3. It groups rules that can safely share one process into a sensor workload.
  4. It lists sensor workers and rejects workers that are inactive, stale, cordoned, over capacity, or missing the required runtime.
  5. It applies hard placement, then scores preferred affinity across the eligible workers.
  6. It writes one leased assignment with a monotonically increasing generation.
  7. The assigned sensor worker starts the process and passes only that workload's rules through ATTUNE_SENSOR_TRIGGERS.
  8. The process includes its workload and assignment generation when it emits an event.
  9. The API rejects targeted events from an expired assignment or from a workload that does not own the target rule.
  10. Rule changes, worker changes, and lease expiry cause the scheduler to recalculate assignments.
Worker failure and reassignment

A lease and generation bound the duplicate-running window and reject stale event producers.

Proposed data model

Use explicit rule field names because an unqualified worker_selector could mean either sensor placement or downstream action placement.

Rule
  sensor_worker_selector       JSONB NOT NULL DEFAULT '{}'
  sensor_worker_tolerations    JSONB NOT NULL DEFAULT '[]'
  sensor_worker_affinity       JSONB NOT NULL DEFAULT '{}'

SensorWorkload
  id                           BIGINT PRIMARY KEY
  sensor_id                    BIGINT NOT NULL
  placement_key                TEXT NOT NULL
  rule_ids                     JSONB NOT NULL
  effective_placement          JSONB NOT NULL
  desired_state                sensor_workload_state NOT NULL

SensorAssignment
  workload_id                  BIGINT PRIMARY KEY
  worker_id                    BIGINT NOT NULL
  generation                   BIGINT NOT NULL
  lease_expires_at             TIMESTAMPTZ NOT NULL
  status                       sensor_assignment_status NOT NULL

sensor_process remains process-health history. It is not a safe assignment record because its current uniqueness is (sensor, worker), which permits several workers to run the same sensor.

How assignment generation is determined

PostgreSQL owns the generation counter for each workload. Workers never choose a generation from a timestamp, process ID, or local counter.

first process authority grant       generation 0 -> 1
lease renewal by current process    generation remains 1
replacement process on same worker  generation 1 -> 2
takeover by another worker          generation 2 -> 3
release or disable                  owner cleared; generation retained
later acquisition                   generation 3 -> 4

The assignment repository locks the workload assignment row and increments generation before every new sensor process receives authority. A lease renewal keeps the current generation. A release clears ownership but does not reset or reuse the counter.

Generation is scoped to workload_id. Two workloads for the same sensor advance independently, so restarting one legitimate sensor instance does not fence another.

Why process launches increment generation A replacement process may start while the old process is slow to exit. Giving the replacement a new generation fences the old process even when both belong to the same worker service and workload lease.

Effective placement

The sensor's owning pack remains the administrative baseline. A cross-pack rule must not substitute its own pack's policy for the sensor pack's policy.

effective hard constraints = sensor-owning pack
                           AND sensor definition
                           AND rule sensor placement

candidate worker = role is sensor
               AND status is active
               AND heartbeat is fresh
               AND cordoned is false
               AND runtime is compatible
               AND capacity is available
               AND effective hard constraints match

Tests that prove the contract

  • Only one worker owns each sensor workload.
  • Rules with different selectors can run on different workers.
  • Rules with compatible placement can share a workload.
  • A process receives only the rules assigned to its workload.
  • Preferred affinity selects the highest-scoring eligible worker.
  • Cordon, stale heartbeat, runtime mismatch, and exhausted capacity exclude workers.
  • A placement-only rule update moves the workload.
  • All create requests, including disabled rules, and all enable requests return 422 when no compatible sensor worker exists.
  • Pack-uploaded and pack-registered rules pass through the same admission path as direct API rule creation.
  • A pack deployment with one incompatible rule returns 422 and persists none of the pack changes.
  • A pack deployment response reports every incompatible rule, not only the first failure.
  • Admission and scheduling use the same eligibility implementation and produce the same result.
  • A worker loss between admission and assignment does not leave an enabled unscheduled rule.
  • A stale assignment cannot emit a targeted event.
  • Initial startup never spawns a process before placement and assignment checks pass.
  • Lease expiry moves a workload without accepting events from the old generation.

Suggested delivery order

  1. Fix current sensor placement defects. Check placement before startup, honor cordon and worker health, validate persisted placement, and document duplicate behavior.
  2. Add global sensor assignment and leases while keeping one workload per sensor.
  3. Add shared worker eligibility and enforce it through API admission before creating or enabling an active rule, or deploying a pack that contains rules.
  4. Add rule placement with the temporary rule that all active constraints must fit one worker.
  5. Add partitioned workloads so rules with incompatible placement can run on different workers.
  6. Bind targeted event creation to the current assignment generation.
  7. Add UI controls and operational views after the assignment API reports useful conflict reasons.
Why this order Rule fields are the easy part. Shipping them before exclusive sensor ownership would make the configuration look precise while several matching workers could still run duplicate copies.

Decisions for review

QuestionRecommended answer
Does rule placement affect the sensor, the action, or both?Sensor only. Use explicitly prefixed field names.
May two rules for one sensor run on different workers?Yes, through separate sensor workloads.
May two workers run one workload?No. One leased assignment owns the workload.
Can rules share a sensor process?Yes, when their effective placement and runtime contract are compatible.
Which pack placement applies to a cross-pack rule?The sensor-owning pack remains mandatory.
What happens for webhook triggers?The API rejects sensor placement because no managed sensor exists.
What happens when all matching workers disappear after activation?The workload becomes unschedulable with a stored, visible reason until a compatible worker returns.
Can the API create or enable a rule when no worker matches?No. Return 422 with stable incompatibility reason codes.
Can the API deploy a pack when one contained rule has no compatible worker?No. Reject the entire deployment with 422, report every failing rule, and persist none of the proposed pack changes.
Does admission guarantee that the worker stays available?No. Assignment must recheck eligibility and acquire a lease before the enabled rule commits.
How does failover avoid stale emitters?The event API checks workload ownership and assignment generation.
